## 1. What one hash asks the machine to do

The API derives an initial state with BLAKE2b, initializes the scratchpad, resets rounding, executes eight chained programs, and finalizes the hash. The intermediate program outputs seed subsequent programs. The batch API combines finalization with preparation of the next input; consequently, batching must be held constant across comparisons. Source: `randomx.cpp`, hash and batch functions.

Inside each main-loop iteration, the interpreter loads integer and floating-point state from the scratchpad, executes the generated bytecode, computes a data-dependent dataset access and prefetch, mixes a dataset line into integer registers, and writes state back to the scratchpad. V2 replaces the F/E XOR mixing step with AES operations. Source: `vm_interpreted.cpp::execute`. This is a semantic map, **not an assertion that JIT host instructions execute in exactly this order or take particular cycle counts**.

The cache/dataset initialization phase is distinct from sustained mining. `benchmark.cpp` initializes memory and VMs before restarting its hashing stopwatch. The Python runner's process timer includes initialization; it must not be divided into nonce count and called sustained hashrate.

## 2. Exact static parameters

| Quantity | V1 | V2 | Interpretation |
|---|---:|---:|---|
| Generated program length | 256 | 384 | VM instruction slots per generated program |
| Iterations per program | 2,048 | 2,048 | Main-loop iterations |
| Programs per hash | 8 | 8 | Chained program executions |
| Nominal VM slots per hash | 4,194,304 | 6,291,456 | Length x iterations x program count |
| Dataset allocation | 2,181,038,016 bytes | Same | 2,080 MiB minus 64 bytes |
| Initialization/light cache | 256 MiB | Same | Not an additional per-thread dataset |
| Scratchpad per VM | 2 MiB | Same | Mutable, not shared between hashing VMs |
| Nested scratchpad regions | 16 KiB / 256 KiB / 2 MiB | Same | Address masks, not mandatory physical L1/L2/L3 cache sizes |

Source: `configuration.h`; arithmetic reproduced by `scripts/workload_profile.py`. The dataset can be shared by multiple VMs in the benchmark; each VM still requires its own scratchpad (`benchmark.cpp` allocation and VM creation).

**Important:** 50% more nominal slots is not 50% more execution time. Branch re-execution, JIT transformations, dependencies, cache hits and overlap with memory stalls all intervene. Nominal slots are neither dynamic VM instructions nor retired native instructions.

Opcode generation weights, grouped from the 256-entry distribution, are integer 120 (46.875%), floating-point 94 (36.71875%), control 26 (10.15625%), and stores 16 (6.25%). These are encoding probabilities, not percentages of cycles, joules or dynamically executed instructions. `FMUL_R`, `FDIV_M`, `FSQRT_R`, high-half integer multiplication and rounding instructions make it unsafe to model the workload as just AES plus RAM.

## 3. What materially changes in v2

The program grows from 256 to 384 slots without growing the dataset or scratchpad. The upstream rationale describes reduced rounding-mode-update frequency (approximately one update per 16 CFROUND executions) and dataset prefetch two iterations ahead rather than one. These changes motivate measurement of latency hiding; they do not prove which resource limits a proposed RISC-V core. Source: `design_v2.md`; the interpreter's v1/v2 memory-register selection is visible in `vm_interpreted.cpp`.

V2's loop AES mixing is especially relevant to an architecture proposal. With four floating-point register pairs, the interpreter applies four AES operations for each of four keys: **16 AES round-function calls per main-loop iteration**, or **262,144 additional calls per hash** at 2,048 iterations x 8 programs. This counts this mixing block only; it is not the total AES work per hash, a host-instruction count, or a cycle estimate. AES also exists outside this block. Source: `vm_interpreted.cpp::execute` and `common.hpp::RegisterCountFlt`.

The same loop consumes one 64-byte dataset line per iteration. The resulting 1,048,576 bytes/hash is **logical dataset payload**, not measured DRAM traffic. Cache behavior, prefetches and memory-system transactions must be measured separately. Similarly, counting scratchpad source loads/stores cannot establish external memory bandwidth.

## 4. Architectural hypotheses to test, not conclusions to assume

| Hypothesis | Controlled investigation | Evidence needed before design work |
|---|---|---|
| Dataset latency limits throughput | Thread scaling; fixed memory configuration; later calibrated latency sweeps | Correct hashes, repeatable throughput, trustworthy stall/memory evidence |
| Scratchpad/cache capacity limits scaling | Per-VM working-set accounting and cache behavior as threads increase | CPU topology, placement, cache/NUMA context; no inference from nominal cache size alone |
| AES execution materially affects v2 | Hardware versus software AES on the same supporting ISA | Matching correctness controls; identical other settings; limitation that software AES is not a custom-hardware energy model |
| Floating-point operations or rounding are limiting | Profile JIT execution and inspect exact instruction mapping | Correct rounding in all required modes; dynamic evidence rather than opcode weights |
| Front-end/branch behavior matters | Compare generated code footprint, instruction/branch counts and throughput | Counter availability, multiplexing, JIT attribution and collection overhead recorded |
| A faster design is more efficient | Time-aligned whole-system power and throughput | Hashes/J at a declared boundary; area/system cost considered later |

Do not turn these hypotheses into an RTL shopping list. No core, cache topology, AES unit or simulator has been selected by this work package.

## 5. Measurement defects found and addressed

`benchmark.cpp` passes CPU ID `-1` in its single-thread path, ignoring its affinity mask. Its multithreaded path prints an affinity failure without necessarily failing the process. The wrapper now rejects one-thread `--affinity` with an explanation to use external process pinning, checks mask capacity/available CPUs, and rejects reported affinity failures. Example on a deliberately chosen allowed CPU: `taskset -c "$CPU" python3 scripts/benchmark.py ...`; first establish `$CPU` from the host's topology, not an assumed CPU 0.

The wrapper now also validates upstream integer bounds; rejects non-finite, non-positive or wrong-unit performance; verifies known hash constants independently of the printed reference; records minimum-duration failures; separates warmup records; and summarizes median/min/max with valid/failed counts. Its schema is now version 2. Consumers must distinguish `phase=warmup` from `phase=measurement`.

`--warmups` performs **separate-process preconditioning**, not same-VM or same-allocation cache warmup. `--min-run-seconds` uses an interval inferred from rounded upstream performance. It is useful for rejecting short trials but **not** for aligning a power meter. Precise steady-state interval markers and same-process warmup remain a follow-on instrumentation task; do not silently patch the vendored benchmark.

## 6. Reproduction and the next experiment

On a Linux checkout, validate the tooling and source first:

```bash
python3 scripts/verify_vendor.py
python3 -m unittest discover -s tests -v
python3 scripts/workload_profile.py --output /tmp/openrx-profile.json
diff -u benchmarks/profiles/pinned-v2.0.1.json /tmp/openrx-profile.json
bash scripts/build.sh
bash scripts/test.sh
```

Run the known full-dataset controls before long trials. Repeat controls for every AES/thread/ISA configuration being compared:

```bash
python3 scripts/benchmark.py --mode mine --versions v1 v2 \
  --threads 1 --init-threads 2 --nonces 1000 --seed 0 --repeats 1
```

For a throughput candidate, after selecting the host and CPU placement:

```bash
python3 scripts/benchmark.py --mode mine --versions v1 v2 \
  --threads 1 --init-threads 2 --nonces 100000 --seed 0 \
  --warmups 1 --repeats 4 --min-run-seconds 30 --timeout 900
```

Use 1, 2, 4 and suitable higher thread counts only where the host's available physical cores/resources justify them. Hold seeds, nonce counts, compiler/build, batch mode, pages, affinity, memory and thermal/power settings constant. Repeat with `--soft-aes` only on a CPU for which the hardware-AES comparison is supported. Four repeats balance the starting v1/v2 order; repeat the AES/configuration matrix in reversed or recorded randomized order to detect drift. Tune nonces and timeout to the slowest configuration, preserving failed/short pilot runs. A long run without an upstream reference remains explicitly `known_reference_matches=null`; obtain an independent trusted expected result for its seed/count before using it as stronger correctness evidence.

Record host model, socket/core/SMT/NUMA layout, CPU quota, cache sizes, RAM channels/speed, OS, compiler, binary hash, exact affinity, pages, thermal and frequency behavior, background load and all raw runs. Captured metadata is a starting point, not proof of isolation. Hardware-counter profiling is separate from uninstrumented throughput trials; record unsupported/denied events and do not change system permissions automatically.

For energy measurements, record meter model, sampling times, synchronization, measurement uncertainty and which components are included. Integrate energy over the actual hashing interval; report completed valid hashes divided by measured joules. Whole-system idle-subtracted energy, CPU-package telemetry and modeled power must remain separate, explicitly labeled metrics. No such readings were collected here.
